# TypeScript Style Guide: Hardhat Projects

This document outlines key TypeScript style conventions for this project, specifically for Hardhat tests and scripts. It is a practical guide adapted from general best practices to fit our tooling.

## 1. Language Features & Conventions

- **Variable Declarations:** Always use `const` or `let`. **`var` is forbidden.** Use `const` by default unless a variable needs to be reassigned.
- **Modules:** Use ES6 modules (`import`/`export`).
- **Exports:**
  - Use named exports (`export { MyClass };`) for shared utilities and constants.
  - **Default exports are acceptable and expected for Hardhat configuration files** (`hardhat.config.ts`).
- **Classes:**
  - Use TypeScript's `private` visibility modifier for non-public members.
  - Mark properties never reassigned outside the constructor with `readonly`.
  - Avoid the `public` modifier, as it's the default.
- **Functions:** Prefer `async/await` for blockchain interactions. Use arrow functions for anonymous callbacks and simple functions.
- **String Literals:** Use double quotes (`"`) to align with Prettier/ESLint defaults often found in Hardhat projects. Use template literals (`` ` ``) for interpolation and multi-line strings.
- **Equality Checks:** Always use triple equals (`===`) and not equals (`!==`).
- **Type Assertions:** Avoid type assertions (`x as SomeType`) and non-nullability assertions (`y!`) where possible. Prefer type guards or explicit checks. If an assertion is necessary, add a comment explaining why it's safe.

## 2. Disallowed & Discouraged Features

- **`any` Type:** **Avoid `any`**. Use `unknown` for unknown values or a more specific type. For contract interactions, rely on TypeChain-generated types.
- **Wrapper Objects:** Do not instantiate `String`, `Boolean`, or `Number` wrapper classes.
- **Semicolons:** Do not rely on Automatic Semicolon Insertion (ASI). **Explicitly end all statements with a semicolon.**
- **`eval()`:** Forbidden.

## 3. Naming Conventions

- **`UpperCamelCase`:** For classes, interfaces, types, enums, and contract types (e.g., `MyContract`).
- **`lowerCamelCase`:** For variables, parameters, functions, methods, and properties.
- **`CONSTANT_CASE`:** For global or module-level constant values.
- **`_` Prefix/Suffix:** **Do not use `_` as a prefix or suffix** for identifiers. This is a common convention in Solidity for unused parameters, but it should be avoided in TypeScript.

## 4. Type System & Hardhat Integration

- **Type Inference:** Rely on type inference for simple, obvious types. Be explicit for complex objects and function signatures.
- **TypeChain:** All contract interactions must be strongly typed using the types generated by TypeChain.
  - Example: `let myContract: MyContract = await ethers.getContract<MyContract>("MyContract");`
- **Ethers.js Types:** Use the types provided by Ethers.js for blockchain-specific objects (e.g., `SignerWithAddress`, `BigNumber`).
- **Optional vs. `| undefined`:** Prefer optional properties in interfaces and types (`?`) over adding `| undefined` to the type.

## 5. Comments and Documentation

- **JSDoc:** Use `/** JSDoc */` for documenting functions and complex logic.
- **Implementation Comments:** Use `//` for single-line comments.
- **Clarity over Redundancy:** Comments should explain *why* something is done, not *what* is being done. Avoid restating the code.
- **TODOs:** Use `// TODO:` to mark areas that need future attention.
